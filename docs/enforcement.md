# Лимиты, сроки, сбросы и вебхуки

Что делает лимит трафика и срок подписки настоящими, и как о каждом таком событии узнаёт
внешний мир.

Код: `internal/service/{enforcement,periods,webhooks}.go`, `internal/worker/{enforcement,webhooks}.go`,
`internal/webhook`, `internal/postgres/queries/{enforcement,webhooks}.sql`.

## Статусы

| Статус | Кто ставит | Кто снимает |
|---|---|---|
| `active` | создание, продление, сброс периода | — |
| `limited` | воркер: `traffic_used >= traffic_limit` | сброс периода, продление, ручной сброс трафика |
| `expired` | воркер: `expires_at` в прошлом | продление |
| `disabled` | оператор | оператор |

Ноды обслуживают только `active`. Любой переход двигает версию конфига нод, которые
обслуживали пользователя, и они снимают или возвращают его **без рестарта ядра** (ADR-065).

## Как быстро срабатывает лимит

Путь: ядро считает → агент опрашивает (`NODE_STATS_INTERVAL`, 30 с) → отправляет на ближайшем
heartbeat (30 с) → воркер принуждения (`ENFORCEMENT_INTERVAL`, 30 с) → нода получает конфиг
на следующем heartbeat (30 с) → снимает пользователя с ядра.

**Худший случай — около двух минут трафика сверх лимита.** Это точность лимита по умолчанию;
уменьшение интервалов её улучшает ценой работы.

**Открытые соединения не рвутся.** Снятый пользователь не может открыть новое соединение, но
то, что уже открыто, ядро дорабатывает. Это поведение Xray, и мы его принимаем: разорвать
соединения одного пользователя ядро не умеет, а рестарт ядра наказал бы за чужой лимит всех
пользователей ноды (ADR-070).

## Сбросы

`reset_strategy`: `never`, `daily`, `weekly` (с понедельника), `monthly`. Начало периода
считается в `BILLING_TIMEZONE`: месяц подписчика в Москве начинается в полночь по Москве, то
есть в 21:00 UTC последнего дня предыдущего месяца.

Сброс обнуляет `traffic_used`, возвращает `limited` в `active` и оставляет `traffic_lifetime`
как есть. `expired` и `disabled` сброс **не** включает: у первого кончилась подписка, а не
трафик, второго выключил человек.

В одном проходе сброс идёт раньше лимитов — иначе пользователь, чей период закончился, пока он
был за лимитом, получил бы событие о лимите за прошлый период (ADR-072).

## Вебхуки

События: `user.created`, `user.limited`, `user.expired`, `user.renewed`.

```bash
curl -s -X POST localhost:8080/api/v1/webhooks -H "Authorization: Bearer $ACCESS" \
  -H 'Content-Type: application/json' \
  -d '{"url":"https://billing.example.com/hooks/panel","events":["user.limited","user.expired"]}'
```

В ответе — `secret`. **Он показывается один раз**; сохранить его сразу.

Доставка — `POST` с JSON:

```json
{
  "event": "user.limited",
  "at": "2026-09-28T12:00:00Z",
  "user": {
    "id": 42, "username": "alice", "xray_email": "k3v9...", "status": "limited",
    "traffic_used": 107374182400, "traffic_limit": 107374182400, "expires_at": null
  }
}
```

Учётных данных в событии нет — ни UUID, ни паролей, ни токена подписки. Нужна ссылка
подписки — её можно получить через API ключом, который отзывается.

### Как проверять на стороне приёмника

```
X-Xraypanel-Event:     user.limited
X-Xraypanel-Delivery:  1234          одинаков на всех попытках — по нему дедуплицировать
X-Xraypanel-Timestamp: 1790000000
X-Xraypanel-Signature: sha256=<hex>
```

1. отвергнуть, если timestamp дальше пяти минут от своих часов;
2. посчитать `HMAC-SHA256(secret, timestamp + "." + сырое тело)` и сравнить с подписью
   **за постоянное время**;
3. если id доставки уже видели — ответить 2xx и ничего не делать.

Эталон — `internal/webhook.Verify`. На Python то же самое:

```python
import hmac, hashlib, time

def verify(secret: bytes, body: bytes, timestamp: str, signature: str) -> bool:
    if abs(time.time() - int(timestamp)) > 300:
        return False
    expected = "sha256=" + hmac.new(secret, timestamp.encode() + b"." + body,
                                    hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, signature)
```

### Гарантии

- **Изменение и событие фиксируются вместе.** Событие ставится в очередь в той же транзакции,
  что и переход статуса. Нет изменения без события и события без изменения.
- **At-least-once.** Приёмник может получить одно событие дважды (ответ потерялся после
  обработки) — отсюда дедупликация по id доставки.
- **Повторы.** Любой ответ кроме 2xx, таймаут (`WEBHOOK_TIMEOUT`, 10 с) или сетевая ошибка —
  повтор через 30 с, 1 мин, 2 мин, … до 6 ч. По умолчанию 12 попыток, это ≈14,5 часа: ночной
  простой приёмника переживается. Потом доставка остаётся в базе с последней ошибкой.
- **Редиректы не выполняются**: 3xx — это неудача, подписанное тело не уходит туда, куда его
  не направлял оператор.

## Диагностика

- **пользователь за лимитом, но работает** — посмотреть `status`: если `active`, воркер ещё не
  прошёл или трафик не дошёл (см. [`traffic.md`](traffic.md)); если `limited`, но нода его
  пускает — `applied_version` ноды отстаёт от `config_version`;
- **сброс не случился** — `reset_strategy` и `last_reset_at`; начало периода считается в
  `BILLING_TIMEZONE`, а не в UTC;
- **вебхуки не приходят** — `webhook_deliveries.last_error` и `attempts`; в логе панели
  `a webhook delivery failed; it will be retried` с причиной.

## Что проверяется тестами

- границы периодов: UTC, Москва, ISO-недели, високосный февраль, новый год, оба перехода на
  летнее время в Берлине — `internal/service/periods_test.go`;
- расписание повторов и окно по умолчанию — `internal/worker/webhooks_test.go`;
- подпись: подделка тела, секрета, сдвиг timestamp, устаревшие доставки; формат зафиксирован
  значением, посчитанным независимо на Python — `internal/webhook`;
- переходы ровно один раз, аудит, событие, уведомление нод; сброс раз в период; сброс не
  воскрешает `expired`/`disabled`; порядок «сброс раньше лимита» —
  `test/integration/enforcement_test.go`;
- доставка: подпись проверяется приёмником, два отказа и успех, повторные проходы не шлют
  второй раз, отказ после последней попытки, секрет показывается один раз;
- **сквозной**: пользователь с лимитом гонит трафик через настоящую ноду и теряет доступ, а
  удерживаемое соединение другого пользователя продолжает возить байты, рестартов ядра ноль —
  `test/integration/billing_test.go`.
