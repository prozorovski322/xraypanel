# Миграции

Инструмент — [goose](https://github.com/pressly/goose), миграции лежат в
`internal/postgres/migrations` и **вкомпилированы в бинарник** через `go:embed`.
Отдельный CLI не нужен: контейнер, в котором есть бинарник, но нет `.sql`-файлов,
это отказ, который мы спроектировали заранее.

```bash
make migrate         # применить всё, что не применено
make migrate-status  # что применено, что нет
```

Панель **отказывается стартовать**, если в БД есть непримененные миграции. Код,
работающий на схеме, под которую он не писался, портит данные тише и дороже, чем
упавший старт.

## Правило: только вперёд

`Down`-миграций нет. Блок `-- +goose Down` в каждом файле намеренно бросает
исключение (см. ADR-012).

Причина: `Down`, который никто никогда не прогоняет на реальных данных, даёт
ложное чувство безопасности и ломается именно в тот момент, когда на него
понадеялись.

Откат схемы = **восстановление из бэкапа**. Процедура ниже.

## Как менять схему

Новый файл с возрастающим номером:

```
internal/postgres/migrations/00002_add_something.sql
```

Шаблон:

```sql
-- +goose Up

ALTER TABLE users ADD COLUMN something text NOT NULL DEFAULT '';

-- +goose Down
-- +goose StatementBegin
DO $$
BEGIN
    RAISE EXCEPTION
        'migrations are forward-only; roll back by restoring a backup (see docs/migrations.md)';
END
$$;
-- +goose StatementEnd
```

Если в миграции есть точки с запятой внутри тела (функция, `DO`-блок), оберните
её в `-- +goose StatementBegin` / `-- +goose StatementEnd`, иначе goose разрежет
её по точкам с запятой.

### Совместимость на время деплоя

Между началом и концом деплоя одновременно работают старая и новая версия кода.
Поэтому каждая миграция обязана быть совместима с **предыдущей** версией кода.

**Добавление колонки** — безопасно, если есть `DEFAULT` или колонка nullable.

**Удаление колонки — в два релиза:**

1. Релиз N: код перестаёт читать и писать колонку. Миграции нет.
2. Релиз N+1: `ALTER TABLE ... DROP COLUMN`.

**Переименование колонки** — не делаем. Это добавление новой, копирование данных,
переключение кода, удаление старой: четыре шага вместо одного, зато без окна, в
котором половина инстансов пишет не туда.

**Тяжёлые индексы:** `CREATE INDEX CONCURRENTLY` нельзя выполнять в транзакции,
а goose по умолчанию оборачивает миграцию в транзакцию. Для такого случая:

```sql
-- +goose NO TRANSACTION
-- +goose Up
CREATE INDEX CONCURRENTLY IF NOT EXISTS users_note_idx ON users (note);
```

Помните, что `CONCURRENTLY` может оставить невалидный индекс при сбое — его
надо будет удалить и создать заново вручную.

## Партиции `traffic_records`

Таблица партиционирована по месяцам. Миграция 0001 создаёт текущий месяц плюс
три вперёд и **DEFAULT-партицию**.

DEFAULT-партиция нужна, чтобы дельта трафика записалась даже если партиция на
нужный месяц не была создана заранее: потерять биллинговые данные из-за
пропущенной фоновой задачи хуже, чем потом перенести строки.

Границы партиций задаются с явным `+00`. Голый литерал даты приводится к
`timestamptz` по session TimeZone, и та же миграция, прогнанная с
`TimeZone=Europe/Moscow`, сдвинула бы все границы на три часа относительно UTC-часов,
по которым ключуются строки.

Воркер (M9) расширяет окно партиций вперёд и следит, чтобы DEFAULT-партиция
оставалась пустой. Если в ней появились строки, создать партицию на
пересекающийся период **не получится** — сначала строки надо перенести.

## Восстановление из бэкапа

Бэкапы снимает сервис `backup` production compose-файла: `pg_dump` по расписанию,
проверка каждого дампа чтением, ротация, которая не удаляет последний хороший. Процедура
восстановления — в [`deployment.md`](deployment.md#восстановление); коротко:

```bash
# В новую базу; рабочая не трогается. Непроверенный дамп не восстанавливается.
docker compose exec backup backup restore panel-20260928T030000Z.dump panel_restored

# Версии миграций восстановленной базы.
docker compose run --rm -e DATABASE_URL=".../panel_restored?sslmode=disable" migrate migrate-status

# Переключение переименованием баз, при остановленных panel, web и backup; затем up -d,
# и migrate доприменит миграции новее дампа.
```

Это проверяется автоматически: интеграционный тест снимает дамп настоящим `pg_dump`,
восстанавливает его в пустую базу, проверяет, что миграций к применению нет, и поднимает
на ней панель, которая должна отдать ту же подписку байт в байт. Job `stack` в CI
повторяет это на собранных образах. Иначе «откат = восстановление из бэкапа» был бы не
процедурой, а её отсутствием.

### Что бэкап не содержит

`PANEL_SECRET_KEY` живёт только в env и **не попадает в дамп**. Без него
восстановленная база бесполезна: не расшифруются приватный ключ CA, ключи
Reality и TOTP-секреты.

Храните ключ отдельно от дампов. Бэкап, в котором лежит и то и другое, — это
бэкап с замком и ключом в одной коробке.
