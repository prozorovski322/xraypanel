# Архитектура

Как устроена система целиком: из чего она состоит, кто с кем разговаривает, где лежит
состояние и что происходит, когда какая-то часть недоступна. Детали каждой части — в
отдельных документах, ссылки по тексту. Решения и их причины — в
[`decisions.md`](decisions.md).

## Источник правды один

Всё состояние — в PostgreSQL панели. Нода **никогда** не ходит в базу и не знает о её
существовании (ADR-001, ADR-003):

- панель собирает из таблиц полный `config.json` для каждой ноды и отправляет его по
  стриму вместе с версией ([`xray-config.md`](xray-config.md));
- нода применяет его, по возможности без рестарта ядра — пользователи и удаление
  inbound'ов идут через API Xray (ADR-009, M8), — и докладывает применённую версию;
- счётчики трафика нода читает из ядра и отправляет батчами с идентификатором; панель
  принимает батч ровно один раз ([`traffic.md`](traffic.md)).

Отсюда главное свойство: любое изменение — это запись в базу плюс увеличение
`config_version` затронутых нод. Доставка изменения — забота протокола, а не того кода,
который изменение сделал.

## Потоки

**Администратор.** Браузер → Caddy → `/api/v1`. Access-токен живёт в памяти SPA,
refresh — в httpOnly-cookie, ротируется на каждом обновлении, повторное использование
отзывает всю цепочку ([`authentication.md`](authentication.md)). Каждое изменение пишет
запись аудита в той же транзакции.

**Подписчик.** Клиент → Caddy → `/sub/{token}` → панель. Формат выбирается по
`User-Agent` или `?format=`. Браузер по той же ссылке получает от Caddy статическую
страницу, которая берёт данные из `/sub/{token}/info`. Токен — единственный
идентификатор, поэтому ответ без токена, с неверным и с отозванным одинаков (404), путь с
токеном не попадает в логи панели, а в Caddy access-лог выключен
([`subscriptions.md`](subscriptions.md)).

**Нода.** Агент сам открывает долгоживущий gRPC-стрим к панели с клиентским сертификатом,
выпущенным CA панели при регистрации по одноразовому токену. Панель узнаёт ноду по
отпечатку сертификата. По стриму вниз идут конфиг и heartbeat, вверх — результат
применения, статус и батчи трафика ([`node-protocol.md`](node-protocol.md)). У ноды нет
входящих портов управления.

**Принуждение.** Воркер каждые 30 секунд переводит пользователей в `limited`/`expired`,
сбрасывает периоды, и каждое такое изменение увеличивает версию конфига нод, где
пользователь есть; нода удаляет его из ядра без рестарта
([`enforcement.md`](enforcement.md)).

**Вебхуки.** События пишутся в очередь в той же транзакции, что и изменение; доставка —
отдельным воркером с HMAC-подписью и повторами до ~14,5 часов.

**Бэкапы.** Отдельный сервис снимает `pg_dump`, проверяет его чтением и публикует под
финальным именем только после проверки.

## Где лежит состояние

| Что | Где | Потеря означает |
|---|---|---|
| Пользователи, ноды, inbound'ы, трафик, аудит | PostgreSQL | восстановление из бэкапа |
| Приватный ключ CA, ключи Reality, TOTP, секреты вебхуков | PostgreSQL, зашифрованы `PANEL_SECRET_KEY` | — |
| `PANEL_SECRET_KEY` | только `.env` панели | перерегистрация нод, перевыпуск ключей Reality, сброс 2FA |
| Идентичность ноды, последний конфиг, неотправленный трафик | bolt-файл в томе ноды | перерегистрация ноды; неотправленные байты |
| Сертификат HTTPS, ACME-аккаунт | том `caddy-data` | повторный выпуск (с лимитами CA) |
| Дампы | том `backups` | ничего, пока база жива; копируйте наружу |

## Отказы

| Что недоступно | Что происходит |
|---|---|
| Панель | Ноды продолжают обслуживать клиентов по последнему применённому конфигу (он в bolt-кэше); после рестарта агента ядро поднимается из кэша. Трафик копится на ноде и дойдёт после восстановления связи. Не работают админка, подписки, новые изменения и принуждение лимитов |
| PostgreSQL | `/readyz` панели красный, запросы API и подписки отвечают ошибкой. Ноды — как выше |
| Нода | Её клиенты без связи через неё; остальные ноды не затронуты. Статус в админке — `disconnected` сразу при обрыве стрима или по таймауту heartbeat |
| Caddy | Недоступны админка и подписки; ноды подключаются к панели напрямую и не затронуты |
| Бэкап | Контейнер становится unhealthy через два пропущенных интервала; на работу панели не влияет |

## Процессы и масштаб

Панель — **один процесс**: HTTP, gRPC и все воркеры живут в нём (ADR-002: без Redis, пока
панель одна). Лимиты запросов, реестр живых нод и кэш CA — в памяти. Вторая реплика
панели потребует вынести их (и ввести Redis или аналог); до тех пор масштаб — 1–5 тысяч
пользователей и 10–30 нод на одной небольшой машине.

Трафик — самая большая таблица: почасовые строки партиционированы по месяцам и живут 90
дней, суточные агрегаты хранятся бессрочно и питают графики.

## Границы доверия

- **Интернет → Caddy.** TLS, HSTS, CSP без inline-скриптов, `Referrer-Policy: no-referrer`.
- **Caddy → панель.** Панель верит `X-Forwarded-For` только от подсети compose-сети
  `edge` (`HTTP_TRUSTED_PROXIES`); от этого адреса зависят лимиты входа, лимит подписки и
  аудит.
- **Нода → панель.** mTLS: нода проверяет панель по пину CA, панель ноду — по сертификату
  своего CA и его отпечатку в базе. Токен регистрации одноразовый и короткоживущий.
- **Панель → нода.** Нода принимает конфиг только по стриму, аутентифицированному выше;
  другого канала управления у неё нет.
- **Секреты.** Один мастер-ключ в окружении; всё остальное в базе зашифровано им
  (AES-256-GCM с привязкой к назначению). Пароли — argon2id, токены — SHA-256.

## Сборка и поставка

| Образ | Dockerfile | Содержимое |
|---|---|---|
| `panel` | `deploy/panel.Dockerfile` | статический бинарник, не root |
| `web` | `deploy/web.Dockerfile` | Caddy + собранный `frontend/dist` без source maps |
| `backup` | `deploy/backup.Dockerfile` | `postgres:16-alpine` + инструмент бэкапов, не root |
| `node` | `deploy/node.Dockerfile` | агент + xray-core с проверкой контрольной суммы релиза |

CI ([`.github/workflows/ci.yml`](../.github/workflows/ci.yml)) на каждый push: сборка,
тесты, линтер, миграции на чистой базе, интеграционные тесты (в том числе снятие и
восстановление дампа реальными `pg_dump`/`pg_restore`), админка и её smoke-тест, образ
ноды, и job `stack` — три образа, поднятые production compose-файлом, с запросами через
Caddy, бэкапом и восстановлением. Релиз
([`.github/workflows/release.yml`](../.github/workflows/release.yml)) по тегу `vX.Y.Z`
публикует четыре образа для amd64 и arm64 в GHCR с SBOM и подписанным provenance.
