# Генерация конфига Xray

Панель собирает **весь** `config.json` и отдаёт ноде готовый блоб. Нода записывает
и применяет, ничего не досочиняя (ADR-003). Локальных конфигов на нодах нет.

Код: [`internal/xray/config`](../internal/xray/config),
Reality: [`internal/xray/reality`](../internal/xray/reality).

## Что генерируется всегда

```
log         уровень логирования
api         tag "api", services HandlerService / StatsService / LoggerService
stats       пустой объект — без него счётчики не собираются вообще
policy      levels.0.statsUser{Uplink,Downlink} + system.statsInbound{Uplink,Downlink}
inbounds    api-inbound (dokodemo-door на 127.0.0.1) + пользовательские
outbounds   freedom "direct" + blackhole "blocked"
routing     правило: inboundTag ["api"] → outboundTag "api"
dns         только если заданы серверы
```

Три вещи, без каждой из которых учёт трафика молча не работает, а конфиг при этом
стартует нормально:

1. секция `stats: {}` — иначе счётчики не собираются;
2. `policy.levels.0.statsUserUplink/Downlink` — иначе нет счётчиков
   `user>>>{email}>>>traffic>>>*`, на которых держится биллинг;
3. `policy.system.statsInboundUplink/Downlink` — иначе нет пер-инбаундных сумм.

На все три есть отдельный тест, потому что «билинг не работает» обнаруживается
через недели.

Api-inbound слушает **только loopback**. Через этот API добавляются и удаляются
пользователи и читаются все счётчики, то есть доступный извне api-порт равносилен
административному доступу к ноде (ADR-033). Тег `api` зарезервирован: на него
смотрит routing-правило, и одноимённый пользовательский inbound получал бы
API-трафик.

## Поддерживаемые комбинации

| Протокол | Транспорт | Security | Замечания |
|---|---|---|---|
| vless | tcp | reality | `flow: xtls-rprx-vision` |
| vless | ws | tls | |
| vless | grpc | tls | |
| vless | xhttp | reality | |
| vless | httpupgrade | tls / none | |
| trojan | ws / tcp / grpc | tls | |
| shadowsocks | tcp | none | только методы `2022-*` |

`flow` эмитится **только** для `vless + tcp + tls|reality`. На ws/grpc/xhttp Xray
его не принимает, и это ловится и констрейнтом в БД, и валидацией генератора
(ADR-010).

Из Shadowsocks поддерживаются только методы `2022-*`. У старых AEAD-шифров нет
пользовательских ключей, то есть многопользовательский inbound на них не может
атрибутировать трафик, и биллинг становится невозможен (ADR-030).

## Reality

Панель генерирует X25519-пару и набор shortId'ов, хранит приватный ключ
зашифрованным, в клиентские ссылки отдаёт публичный.

```go
pair, _ := reality.GenerateKeyPair()   // base64url без padding, как у `xray x25519`
ids, _  := reality.GenerateShortIDs(reality.DefaultShortIDCount)
```

Детали, которые важны:

- **Кодирование — unpadded base64url.** Именно это печатает `xray x25519` и именно
  это читают клиенты. Standard base64 прошёл бы через Go и был бы отвергнут клиентом.
  Есть тест, сверяющий наш вывод с `xray x25519 -i` побайтово: расхождение хотя бы
  в алфавите дало бы сервер, который поднимается чисто, и клиентов, падающих на
  handshake без внятных логов.
- **shortId никогда не пустой.** Пустой shortId Reality трактует как «принимать
  клиента, который не присылает его вовсе», то есть список превратился бы в
  необязательную проверку. Генератор его не выдаёт, валидатор отвергает.
- **`dest` обязан быть `host:port`.** Голое имя не доопределяется до `:443`: молча
  предположенный порт даёт inbound, который работает до того дня, когда кто-то
  направит его на хост с TLS на другом порту.
- **Публичный ключ можно восстановить** из приватного (`reality.PublicKeyFor`), так
  что потеря публичной половины не требует перегенерации пары — иначе все выданные
  ссылки стали бы недействительны.

## Два уровня переопределения

Оба существуют, потому что схема никогда не покроет всё, но у них разная область.

**`inbounds.extra`** — JSON-объект, мержится в готовый объект инбаунда **последним**,
то есть может переопределить что угодно из сгенерированного. Escape hatch, который
не может переопределять, — не escape hatch.

**`nodes.config_patch`** — RFC 7386 merge patch, применяется к **готовому документу**
целиком. Единственный поддерживаемый способ сделать одну ноду отличной от других.

```json
{
  "log": {"loglevel": "debug"},
  "outbounds": [{"protocol": "freedom", "tag": "direct"}],
  "dns": null
}
```

`null` **удаляет** ключ — так убирается то, что эмитит генератор. Массивы
заменяются целиком, поэлементного слияния в RFC нет: переопределяя `outbounds`,
задавайте весь список (ADR-031).

Всё, что используется дважды, должно получить колонку, а не жить в `extra`.
Причина — в ADR-010: поле, о котором знает только один из двух генераторов
(конфига и ссылок), даёт правильный сервер и нерабочую ссылку.

## Хэши и рестарты ядра

`Generate` возвращает не только JSON:

```go
type Generated struct {
    JSON           []byte
    StructuralHash string
    InboundHashes  map[string]string   // по тегу инбаунда
}
```

Рестарт ядра рвёт **все** живые соединения, поэтому он должен случаться ровно
тогда, когда без него нельзя.

- **`StructuralHash`** покрывает всё, кроме пользовательских инбаундов: `log`, `api`,
  `stats`, `policy`, `outbounds`, `routing`, `dns`, плюс api-inbound и его порт.
  Изменился — нужен graceful-рестарт.
- **`InboundHashes`** — по одному на пользовательский inbound. Диффом ноды решается,
  какие inbound'ы добавить или убрать через `HandlerService`, не трогая остальные.

Свойства, закреплённые тестами:

- добавление или удаление пользователя **не** двигает `StructuralHash`;
- добавление inbound'а **не** меняет хэши остальных;
- смена `log`, `api`-порта, `dns`, `routing` или `outbounds` (в том числе патчем)
  двигает `StructuralHash`.

Хэши считаются **после** применения патча: иначе патч мог бы изменить структурную
часть, и нода не узнала бы, что нужен рестарт (ADR-032).

## Детерминизм

Конфиг строится из `map[string]any`, поэтому ключи в файле отсортированы по алфавиту,
а не идут привычным `log`/`api`/`inbounds`. Это сделано намеренно: нода сравнивает
хэши, и генератор, переупорядочивающий собственный вывод, превратил бы **каждый**
опрос в «конфиг изменился» и рестарт ядра. Файл читает Xray, не человек (ADR-034).

Есть тест, генерирующий один spec шесть раз и требующий побайтового совпадения.

## Валидация

Проверки идут в трёх местах, и дублирование намеренное:

1. **Констрейнты БД** — `flow` только где положено, reality требует ключ,
   shadowsocks требует метод и серверный ключ.
2. **`Spec.Validate()`** — то же плюс то, что в SQL не выразить: коллизии портов и
   тегов в пределах ноды, дубли stats-ключей, согласованность ключей Reality.
3. **Настоящий `xray run -test`** в тестах.

Коллизия портов — та ошибка, ради которой всё это есть: два инбаунда на одном порту
означают, что Xray **не стартует вовсе**, панель при этом считает конфиг
доставленным, а снаружи это выглядит как «нода сломалась» без указания причины
(ADR-011). Генератор в этом случае падает и конфиг не отдаёт.

Дубль stats-ключа тоже отвергается: два клиента под одним ключом слили бы трафик в
один счётчик, и одному из них выставили бы чужие байты.

## Тесты

```bash
go test ./internal/xray/...                      # golden + валидация spec'ов
XRAY_BINARY=/path/to/xray go test ./internal/xray/...   # плюс проверка настоящим Xray
make golden                                      # перегенерировать golden-файлы
```

Golden-файлы в [`internal/xray/config/testdata`](../internal/xray/config/testdata).
Перегенерировав их, **посмотрите диff**: golden-файл полезен только пока кто-то
читает записанное в нём изменение.

На момент M3 Xray **26.3.27** принимает все восемь генерируемых комбинаций, и
публичные ключи Reality совпадают с `xray x25519` побайтово. Версия зафиксирована
в CI; при её подъёме именно эти тесты покажут расхождение.
