# Node agent

Data plane: один процесс на ноде, который держит локальный xray-core в том состоянии,
которое хочет панель. Протокол описан в [`node-protocol.md`](node-protocol.md); здесь —
устройство самого агента и эксплуатация.

Код: `cmd/nodeagent`, `internal/agent/{config,store,supervisor,link}`.

## Один образ, агент как PID 1

Агент — PID 1 в контейнере, xray — его дочерний процесс. Не два контейнера, потому что
вся работа агента — управлять именно этим процессом: запустить, дождаться, пока он начнёт
обслуживать, заметить смерть, перезапустить, остановить. Разделение означало бы супервизор,
который разговаривает с container runtime, — ещё одна вещь, которая может сломаться на
каждой ноде.

`network_mode: host` — не оптимизация. Клиенты приходят напрямую на порты, которые
назначает панель; Reality нужен настоящий адрес источника; проброс портов означал бы
правку compose-файла при каждом изменении inbound'а.

## Что происходит при старте

```
1. прочитать конфигурацию из env, свалиться с внятной ошибкой, если её нет
2. открыть bolt-стор в /var/lib/xraypanel-node/agent.db
3. поднять ядро из локального кеша          <-- панель ещё не спрошена
4. если идентичности нет — зарегистрироваться по токену
5. подключиться, сказать Hello, получить HelloAck
6. применять ApplyConfig, отправлять Heartbeat, пока стрим жив
7. при обрыве — backoff с jitter и заново с шага 4
```

Порядок шагов 3 и 5 — это главное решение (ADR-059). Нода, перезагрузившаяся во время
аварии панели, обслуживает тех же пользователей, что и до перезагрузки, и только потом
начинает звонить. Авария control plane не обязана быть аварией сервиса.

## Локальное состояние

Bolt-файл в volume, три записи:

| Запись | Что в ней |
|---|---|
| `identity` | node_id, сертификат, приватный ключ, CA, срок |
| `config` | последний **подтверждённый** конфиг: версия, JSON, хэши |
| `pending` | конфиг, применение которого было прервано |
| `counters` | снимок счётчиков ядра и время старта процесса, которому они принадлежат |
| `traffic` | дельты трафика, свёрнутые по (час, пользователь), ещё не отправленные |
| `batches` | отправленные батчи, которые панель ещё не подтвердила |

Приватный ключ лежит в открытом виде, и это осознанно: шифровать его можно только ключом,
который лежит на том же томе. Защита — права 0600 и то, что том принадлежит ноде; на ноде,
чей диск читает атакующий, на том же диске лежат учётные данные всех пользователей.

`pending` существует потому, что агент можно убить между записью конфига и подтверждением.
Без него такой агент возвращался с пустым кешем и ждал панель — то есть ровно в сценарии,
для которого кеш и нужен. С ним он поднимает прерванный конфиг, но докладывает панели
**предыдущую подтверждённую** версию: он не знает, работает ли новая, и сообщив о ней,
лишил бы себя единственного способа это выяснить.

## Применение конфига

Сначала агент решает, нужен ли рестарт вообще. Дешёвый путь:

```
сравнить с тем, что запущено      -> нельзя сравнить: рестарт
xray run -test на временном файле  -> отвергнут: рабочий конфиг не тронут
атомарная подмена config.json      <- до операций: упавшее ядро поднимут с новым конфигом
операции на живом ядре по API      -> любая неудача: рестарт с новым конфигом
сверка фактического состава с желаемым
запись подтверждения в bolt
ApplyResult наверх (restarted=false)
```

Дорогой путь — тот же, но вместо операций рестарт:

```
xray run -test на временном файле   -> отвергнут: рабочий конфиг не тронут
атомарная подмена config.json
рестарт ядра
ожидание api-порта                  -> не поднялся: откат на предыдущий конфиг
запись подтверждения в bolt
ApplyResult наверх (restarted=true)
```

Готовность — это принимающий api-порт, а не «процесс запустился» (ADR-062). Адрес порта
читается из применяемого конфига, потому что `config_patch` может его передвинуть.

Откат (ADR-057) закрывает случай, который `run -test` не ловит: конфиг, проходящий
проверку и падающий на старте (занятый порт, отсутствующий файл сертификата). Панель
остаётся единственным источником правды — нода продолжает выполнять последнее состояние,
которое панель ей дала, и докладывает об отказе.

Пустой `config_json` означает «ничего не запускать»: нода без inbound'ов или без активных
пользователей останавливает ядро.

## Что делается без рестарта

Рестарт ядра рвёт все живые соединения на ноде. Для пользователя, который в этот момент
что-то смотрит, это неотличимо от поломки сервиса, — а изменения состава пользователей на
работающей установке происходят десятки раз в час. Поэтому:

| Изменение | Что делает агент |
|---|---|
| пользователь добавлен, удалён, перевыпущен | операции на живом ядре, рестарта нет |
| сменился `flow` | пользователь снимается и добавляется заново, рестарта нет |
| inbound снят с ноды | `RemoveInbound` по тегу, рестарта нет |
| inbound добавлен | **рестарт** |
| у inbound'а сменился порт, транспорт, security, ключи | **рестарт** |
| изменилась структурная часть (routing, dns, outbounds, policy, api) | **рестарт** |
| ядро не запущено, или сравнить не с чем | **рестарт** |

Асимметрия между «снять inbound» и «добавить inbound» — не недоделка, а цена контракта
ядра: снятие принимает один тег, добавление — целиком собранный внутренний конфиг со
всеми транспортами, TLS и Reality. Обоснование и отвергнутые варианты: ADR-065.

Решение принимается по хэшам, которые считает панель: структурному и по одному на inbound.
Хэш inbound'а не включает список пользователей — иначе каждый новый пользователь выглядел
бы как изменение, требующее рестарта (ADR-066).

После операций агент спрашивает у ядра фактический состав пользователей на затронутых
inbound'ах и сверяет с желаемым. Это страховка под то, что сообщения API описаны в этом
проекте вручную: единственная ошибка, которую не поймает ни компилятор, ни wire-формат, —
сообщение, которое ядро примет и проигнорирует. Расхождение приводит к рестарту, а не к
тихо неработающему пользователю.

Рестарт остаётся универсальным запасным путём: конфиг к моменту операций уже лежит на
диске, поэтому рестарт с любого места сходится к желаемому состоянию.

Одна особенность ядра, проверенная на живом Xray 26.3.27 и важная для принуждения (M10):
снятие пользователя с inbound'а отвергает его **новые** подключения, но не разрывает уже
открытые. Пользователь, исчерпавший лимит посреди загрузки, докачает её по текущему
соединению. Это зафиксировано тестом в `runtime_test.go`, чтобы M10 решал, оставить так,
или принуждение должно делать что-то ещё.

## Учёт трафика

Агент опрашивает счётчики ядра каждые `NODE_STATS_INTERVAL` и копит дельты в bolt — это
происходит независимо от того, доступна ли панель: трафик идёт и во время аварии, и нода,
перестающая считать на это время, была бы нодой, чьих пользователей за это время не
посчитали. Батчи отправляются на том же такте, что heartbeat, и удаляются только после
подтверждения панелью.

Подробно, вместе с тем, что именно теряется и почему: [`traffic.md`](traffic.md).

## Если ядро умирает само

Watcher перезапускает его с растущим backoff'ом (1 с → 1 мин) и считает перезапуски;
счётчик виден панели. Ядро, которое **ни разу** не стало готовым, автоматически не
перезапускается: это отказ, о котором докладывает тот, кто вызвал применение (ADR-058).

## Конфигурация

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `NODE_PANEL_ADDR` | — | `host:port` порта нод панели, обязательна |
| `NODE_CA_PIN` | — | отпечаток CA панели, обязателен |
| `NODE_ENROLLMENT_TOKEN` | — | одноразовый токен, нужен только до регистрации |
| `NODE_DATA_DIR` | `/var/lib/xraypanel-node` | том с состоянием |
| `NODE_XRAY_BINARY` | `/usr/local/bin/xray` | исполняемый файл ядра |
| `NODE_HEARTBEAT_INTERVAL` | `30s` | пока панель не скажет своё значение |
| `NODE_STATS_INTERVAL` | `30s` | как часто читаются счётчики трафика |
| `NODE_STATS_STRATEGY` | `delta` | `delta` или `reset`; см. [`traffic.md`](traffic.md) |
| `NODE_RECONNECT_MIN` / `MAX` | `1s` / `1m` | границы backoff'а |
| `NODE_LOG_LEVEL` / `FORMAT` | `info` / `json` | лог |

Первые три значения оператор получает из одного ответа панели:

```bash
curl -s -X POST https://panel.example.com/api/v1/nodes/1/enrollment-tokens \
  -H "Authorization: Bearer $ACCESS"
```

Пин обязателен и после регистрации: агент, забывший его, при следующей перерегистрации
вынужден был бы доверять тому, кто ответит.

## Развёртывание

```bash
docker build -f deploy/node.Dockerfile --build-arg XRAY_VERSION=v26.3.27 -t xraypanel-node .
# на ноде: заполнить три переменные в deploy/docker-compose.node.yml
docker compose -f docker-compose.node.yml up -d
```

Версия xray фиксируется аргументом сборки и проверяется по опубликованному дайджесту до
распаковки: нода запускает этот бинарник с сетевыми привилегиями, и взять его на доверие
означало бы сделать сборку самым слабым звеном системы.

## Диагностика

**Нода не появляется в панели.** Лог агента говорит, на чём именно он остановился:

- `no such enrollment token` / `already used` / `expired` — причина в логе **панели**,
  наружу она не сообщается специально (ADR-056);
- `does not match the pinned key` — неверный `NODE_CA_PIN` или агент звонит не туда;
- `certificate is not registered` — нода перевыпущена или удалена; нужен новый токен.
  Агент **не** выбрасывает свою идентичность в этом случае (ADR-063) и продолжает
  обслуживать пользователей из кеша.

**Нода подключена, xray не работает.** `xray_running: false` в
`GET /api/v1/nodes/{id}/connection`; `last_error` в `GET /api/v1/nodes/{id}` содержит
причину последнего отказа применения. В логе контейнера — вывод самого ядра: агент не
перехватывает его, а наследует stdout, чтобы он попадал туда, куда оператор и так смотрит.

**Пользователи жалуются на обрыв после изменения.** Значит применение прошло рестартом.
Каждый рестарт ядра записывается в аудит как `node.core_restarted` с версией конфига, а в
логе агента видно причину: `restarting the core reason=...`. Список изменений, которые
рестарт вызывают, — в таблице выше.

**Нода отстаёт по версии.** `applied_version` меньше `config_version`. Панель дошлёт
конфиг на следующем heartbeat'е; если версия не применяется повторно — значит нода её уже
отвергла, и текст в `last_error`. Повтор той же версии происходит при переподключении или
при смене версии (ADR-060).

## Что проверяется тестами

`internal/agent/supervisor` — с настоящим дочерним процессом (подставной бинарник под
`testdata`, который умеет отвергать конфиг, не стартовать, не слушать и умирать по
расписанию). Мок процесса проверял бы мок.

`test/integration/agent_test.go` — настоящая панель, настоящий агент, настоящий xray:

- регистрация с нуля, пуш конфига, **xray слушает порт, который набрал бы клиент**;
- добавление пользователя доезжает до ноды без вмешательства;
- остановка панели не роняет xray, агент переподключается сам;
- агент, перезапущенный при недоступной панели, поднимает ядро из кеша;
- отвязка последнего inbound'а останавливает ядро, нода остаётся подключённой;
- агент без идентичности и без токена останавливается с внятной ошибкой;
- невозможный пин отвергается при старте, а не при первом рукопожатии.

`test/integration/runtime_test.go` — то же, но с настоящим клиентом, который держит
соединение через ноду на настоящий echo-сервер:

- пользователь добавлен — **соединение другого пользователя продолжает возить байты**, и
  новый пользователь подключается;
- пользователь удалён — новые подключения под его учётными данными отвергаются, чужое
  соединение живо;
- inbound снят — соединение на оставшемся inbound'е живо;
- порт inbound'а переехал — рестарт произошёл, записан в аудит, нода сошлась на новый порт.

Планировщик проверяется отдельно и без ядра (`internal/agent/reconcile`): что именно
считается поводом для рестарта — это решение, а не деталь реализации, и ошибка в нём стоит
либо лишних обрывов, либо ноды, тихо обслуживающей не то, что просили.
