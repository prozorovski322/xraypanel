# Аутентификация

Два вида вызывающих: **администратор** (человек, access-токен) и **API-ключ**
(машина, скоупы). Оба приходят в заголовке `Authorization: Bearer <...>`, и вид
определяется формой самого значения, а не отдельным заголовком — клиент не может
выбрать, как его будут проверять.

## Модель токенов

| | Живёт | Где хранится у клиента | Отзывается |
|---|---|---|---|
| access | 15 мин | в памяти SPA | через `tokens_valid_from` |
| refresh | 30 дней | httpOnly cookie | ротацией и отзывом цепочки |
| MFA-тикет | 5 мин | в памяти SPA | истечением |

Access-токен и MFA-тикет подписываются **разными** ключами, выведенными из
`PANEL_SECRET_KEY` через HKDF. Забыть проверить тип токена тогда означает
несовпадение подписи, а не повышение привилегий.

Refresh-токен не возвращается в теле ответа — только в `httpOnly` cookie,
scope'нутой на `/api/v1/auth`. Скрипт на странице не может его прочитать, и он не
уезжает с каждым посторонним запросом.

## Первый вход

Первый администратор создаётся из окружения при старте, один раз:

```bash
BOOTSTRAP_ADMIN_USERNAME=root
BOOTSTRAP_ADMIN_PASSWORD='correct horse battery staple'
```

Повторный запуск ничего не делает, если администратор уже есть — иначе пароль,
оставшийся в env-файле, был бы постоянным бэкдором, восстанавливающимся при каждом
рестарте. **Уберите эти переменные после первого входа.**

Либо из командной строки (пароль читается из stdin, чтобы не попасть в историю
шелла и в список процессов):

```bash
printf '%s' 'correct horse battery staple' | ./panel admin create root superadmin
```

## Сценарий curl

Дальше `$API=http://localhost:8080/api/v1`. Cookie-jar нужен, потому что refresh
ездит в cookie.

### Вход без 2FA

```bash
curl -sc cookies.txt -X POST "$API/auth/login" \
  -H 'Content-Type: application/json' \
  -d '{"username":"root","password":"correct horse battery staple"}'
```

```json
{"access_token":"eyJhbGciOi...","expires_at":"2026-09-27T05:45:00Z","username":"root","role":"superadmin"}
```

Сохраните токен и проверьте, кто вы:

```bash
ACCESS=$(curl -sc cookies.txt -X POST "$API/auth/login" \
  -H 'Content-Type: application/json' \
  -d '{"username":"root","password":"correct horse battery staple"}' \
  | python -c 'import json,sys; print(json.load(sys.stdin)["access_token"])')

curl -s "$API/auth/me" -H "Authorization: Bearer $ACCESS"
```

```json
{"kind":"admin","username":"root","role":"superadmin"}
```

### Обновление токена

```bash
curl -sb cookies.txt -c cookies.txt -X POST "$API/auth/refresh"
```

Возвращает новый access-токен и **новую** cookie. Старый refresh-токен мёртв.

### Выход

```bash
curl -sb cookies.txt -X POST "$API/auth/logout" -i | head -1     # 204, cookie стёрта
curl -s -X POST "$API/auth/logout-all" -H "Authorization: Bearer $ACCESS" -i | head -1
```

`logout` убивает одну сессию, `logout-all` — все и вместе с ними все выданные
access-токены.

### Включение 2FA

```bash
curl -s -X POST "$API/auth/totp/enroll" -H "Authorization: Bearer $ACCESS"
```

```json
{"secret":"JBSWY3DPEHPK3PXP","uri":"otpauth://totp/xraypanel:root?..."}
```

`uri` скормите QR-генератору, `secret` — для ручного ввода. **2FA пока НЕ включена.**
Её надо подтвердить кодом:

```bash
curl -s -X POST "$API/auth/totp/confirm" \
  -H "Authorization: Bearer $ACCESS" -H 'Content-Type: application/json' \
  -d '{"code":"123456"}' -i | head -1    # 204
```

Два шага не для красоты: включение сразу заперло бы снаружи любого, у кого
приложение не считало QR-код, а выбираться из этого можно только через shell на
сервере.

Подтверждение сдвигает `tokens_valid_from`, поэтому текущий access-токен
перестаёт работать — войдите заново.

### Вход с 2FA

Шаг пароля теперь отдаёт только тикет:

```bash
curl -s -X POST "$API/auth/login" -H 'Content-Type: application/json' \
  -d '{"username":"root","password":"correct horse battery staple"}'
```

```json
{"mfa_required":true,"mfa_token":"eyJhbGciOi..."}
```

Сессии ещё нет. Второй шаг:

```bash
curl -sc cookies.txt -X POST "$API/auth/login/mfa" \
  -H 'Content-Type: application/json' \
  -d '{"mfa_token":"eyJhbGciOi...","code":"123456"}'
```

Код одноразовый. Повторная отправка того же кода в том же 30-секундном окне даёт
401 `invalid_code`, и в логе появляется предупреждение: кто-то отправляет код,
который он **подсмотрел**, а не сгенерировал.

### Выключение 2FA и смена пароля

```bash
curl -s -X POST "$API/auth/totp/disable" \
  -H "Authorization: Bearer $ACCESS" -H 'Content-Type: application/json' \
  -d '{"password":"correct horse battery staple"}' -i | head -1

curl -s -X POST "$API/auth/password" \
  -H "Authorization: Bearer $ACCESS" -H 'Content-Type: application/json' \
  -d '{"current_password":"old one","new_password":"a different passphrase"}' -i | head -1
```

Пароль требуется и для выключения 2FA: иначе перехваченная сессия могла бы тихо
снять второй фактор и остаться в аккаунте.

Смена пароля отзывает **все** сессии и все access-токены. Пароль меняют, когда
подозревают компрометацию, и сессия атакующего не должна это переживать.

### Потерянный аутентификатор

Кодов восстановления нет намеренно. Тот, кто может их применить, и так имеет shell
на сервере, а таблица кодов — это ещё один секрет, который надо хранить и который
можно потерять. Восстановление — с сервера:

```bash
./panel admin reset-2fa root
```

Снимает второй фактор и отзывает все сессии этого администратора.

## API-ключи

```bash
curl -s -X POST "$API/api-keys" \
  -H "Authorization: Bearer $ACCESS" -H 'Content-Type: application/json' \
  -d '{"name":"ci","scopes":["users:read","stats:read"]}'
```

```json
{"id":1,"name":"ci","prefix":"k3m9qp2wxd","scopes":["users:read","stats:read"],
 "key":"xpk_k3m9qp2wxd_7f2k...","created_at":"2026-09-27T05:30:00Z"}
```

`key` показывается **один раз**: в БД лежит только его SHA-256. Префикс
некритичен и виден в списке — по нему утёкший ключ опознаётся и отзывается без
того, чтобы кто-то вставлял секрет целиком в чат. Маркер `xpk_` делает ключи
находимыми grep'ом и сканерами секретов.

```bash
curl -s "$API/api-keys" -H "Authorization: Bearer xpk_k3m9qp2wxd_7f2k..."
curl -s -X DELETE "$API/api-keys/1" -H "Authorization: Bearer $ACCESS" -i | head -1
```

### Скоупы

| Скоуп | Что даёт |
|---|---|
| `users:read` / `users:write` | подписчики |
| `nodes:read` / `nodes:write` | серверы |
| `inbounds:read` / `inbounds:write` | inbound'ы и hosts |
| `stats:read` | статистика |
| `admins:read` / `admins:write` | администраторы и ключи |
| `audit:read` | журнал аудита |

`:write` подразумевает `:read` для того же ресурса. Неизвестный скоуп при создании
**отвергается**, а не отбрасывается: иначе ключ с опечаткой выглядел бы в интерфейсе
привилегированным, а на деле не работал, и ошибка вылезла бы позже как непонятный 403.

Ключ без скоупов не может ничего — это безопасное поведение по умолчанию для
недописанного запроса на создание.

Роли администраторов проверяются отдельно: `superadmin` и `admin` могут всё,
`viewer` — только чтение. Права `viewer` выводятся из суффикса скоупа, а не из
списка на роль, поэтому новый `:write`-скоуп в следующей вехе будет запрещён
ему по умолчанию, а не разрешён по забывчивости.

## Ограничение попыток

Два независимых счётчика за окном `AUTH_LOGIN_WINDOW` (дефолт 15 мин):

- **по имени пользователя** — останавливает подбор одного аккаунта с многих адресов;
- **по IP** (порог втрое выше) — останавливает перебор одного пароля по многим
  аккаунтам, чего счётчик по имени не увидит, потому что на каждый аккаунт придётся
  одна-две неудачи.

Превышение даёт `429` с `Retry-After`. Блокировка отсчитывается от **последней**
неудачи, а не от начала окна: иначе можно было бы стучать ровно по краю окна.

Счётчик сбрасывается только **полностью завершённым** входом. Это важно при
включённой 2FA: сбрасывай его на шаге пароля — и тот, кто пароль уже знает, подбирал
бы шестизначный код бесконечно, обнуляя счётчик повторным вводом пароля.

## Что ответы намеренно не различают

Один и тот же `401 invalid_credentials` возвращается на:

- неверный пароль,
- несуществующего пользователя,
- отключённый аккаунт.

Любое различие здесь — бесплатный оракул для перечисления аккаунтов. По той же
причине неверный и **переигранный** TOTP-код дают одинаковый `401 invalid_code`,
хотя в логе они различаются, и replay пишется уровнем `WARN`.

Отсутствующий пользователь вдобавок проверяется против подставного хэша, чтобы
время ответа не выдавало, существует ли аккаунт.

Реальная причина всегда есть в логе, а в ответе есть `request_id`, по которому её
там находят.

## Коды ошибок

| HTTP | `code` | Когда |
|---|---|---|
| 400 | `bad_request` | тело не JSON, неизвестное поле, слишком большое |
| 401 | `invalid_credentials` | неверный пароль / нет пользователя / аккаунт отключён |
| 401 | `invalid_code` | неверный или переигранный TOTP |
| 401 | `invalid_token` | битый, просроченный или отозванный токен |
| 403 | `forbidden` | не хватает скоупа, либо cross-origin refresh |
| 409 | `conflict` | имя занято, 2FA уже включена или не настроена |
| 422 | `unprocessable` | слабый пароль, неизвестный скоуп |
| 429 | `too_many_attempts` | блокировка, см. `Retry-After` |

Неизвестное поле в теле — это `400`, а не «проигнорируем»: на запросе смены пароля
разница между внятной ошибкой и молча не изменившимся паролем существенна.

## CSRF

Refresh-cookie выставлена с `SameSite=Strict`, поэтому в любом современном браузере
она вообще не уедет с cross-site запросом. Вторая линия — проверка `Origin` на
`/auth/refresh`: если заголовок есть и его хост не совпадает с `Host`, запрос
отвергается с `403`. Когда `Origin` отсутствует, запрос пропускается — иначе
поломались бы same-origin клиенты, которые его не присылают.

## Что ещё стоит знать

`PANEL_SECRET_KEY` выводит ключи подписи токенов. Его смена **немедленно** делает
недействительными все access-токены и MFA-тикеты (refresh-токены выживают, они
случайные и лежат в БД хэшами) и ломает расшифровку TOTP-секретов — администраторам
придётся настроить 2FA заново.

Все сравнения времени идут по часам **приложения**, а не базы: `iat` токена ставит
панель, и сравнивать его с `now()` из Postgres означало бы сравнивать двое
независимых часов, расхождение между которыми тихо сдвигает срок жизни токенов.
